We have extended the pruning experiment towards starting pruning from before the vision encoder - and what we have so far is very promising. The patches have to be removed in 2x2 grid groups since there is a grid pooling at the end of the ViT layer - and doing so gives us same ratio of pruned tokens being fed to the LLM backbone. So far, the performance knee occurs at 50 percent pruning compared to 75 percent pruning for the post-ViT experiment, and this is completely understandable since the post-ViT tokens retain a lot of global information. So far, the speedup is very great, and combining with blended actions, we are now very close to real-time deployment while having less visible planning gaps. The next thing to do is to either fine-tune on the reduced token space or do some attention feedback to prune the tokens early in the model so that we dont have much tokens to process anyways.

We decided to do the pruning in a guided manner instead of completely random grouped-patch pruning before the ViT or random token pruning after the ViT - the notion is that an attention score signal from the actual language prompt would provide a clean guidance on which tokens are task relevant or not and can be pruned. The first initial attempts failed, but then we managed to find suitable heatmaps following the work BlindVLA (https://arxiv.org/pdf/2510.25616) where the authors mention that mid level VLM features have the most relevant signals that conditions the visual features to the target task. We have seen heatmaps on libero based on that, and that seemed very promising as the focus was mostly around the task focused regions for the most part, and the focal region shifted based on which stage of the task we were at. So we decided to do a guided pre-ViT token pruning - not in a feedback fashion, but in a dual forward pass fashion to establish a proof of concept for this. We are not able to do the feedback yet cause the scene changes based on action and the regions also change, so using feedback to prune the vision inputs means we are using delayed feedbacks to prune parts of scene that we dont know are useful or not.

The feedforward - pruning pre-ViT experiment did not go well at all. We tried both pruning the visual features 'per-view' and across views for the tokens, but neither gives better results than the random pre-ViT training. So we moved on to attention scores from the diffusion actor network instead of taking the score from the LLM backbone - cause the actor would actually know the most task-relevant parts. Now this method was much better than the text conditioned pruning method, but still lagged behind the random pre-ViT pruning method and did not do well in the overall task. Now we have to look at if this can be done post-ViT and see if the pruning performs better when done post-ViT in a guided fashion using a task feedback. We also need to look at other interpretability/attention heatmap works to better understand or find better feedback methods, and also need to figure out an appropriate way to do the feedback in general.

#### Action smoothness ablation study agent:
We want to do more research around pruning/adaptation. This is not related to the cross-embodiment porting tasks, this is related to the random token dropping ablation studies. Here is our current idea:

Part 2 — VLA-WM hybrids and "plan ahead while executing"
What you're describing — "no matter how fast the planner is, it stops to decide, so motion is never smooth" — is a named, well-studied problem, and there are two distinct families that attack it. They're complementary, and you likely want both.
Family A — asynchronous execution (the direct fix for the stop-and-decide gap). The single most relevant work is Real-Time Chunking (RTC) from Physical Intelligence. They name your exact problem: π0/π0-FAST/π0.5 executed chunks synchronously — finish a chunk, stop, run inference, start the next — and those boundary pauses "aren't in the training data... slow things down, are ugly to look at." RTC's fix is to generate the next chunk while executing the current one, "freezing" the actions already committed and "inpainting" the rest — it literally poses chunk-switching as an inpainting problem. Crucially for you: it works on any flow- or diffusion-based VLA with no retraining — which is exactly MolmoAct2's flow-matching DiT action expert. This is a drop-in candidate. Boundary-smoothness refinements built on it: POTR (kills the acceleration/jerk spikes RTC leaves at chunk boundaries), FASTER (faster first-action latency), and A2C2 (a per-step correction head).

We want to explore ways to invoke the planner agent multiple times in middle of an action execution in order to generate continuous motion instead of halting every now and then. For this experiment, we might want to run it on either the real-time or the synchronous interactive demos. The idea is that we want to invoke the planner as soon as observations are available, and based on how many steps have been taken so far in real time, we interpolate between the actions / leave behind new samples and blend in new actions so that the model keeps reacting to the environment in between the action horizon of 15 steps - to make the whole thing run faster at the expense of more compute overall.
